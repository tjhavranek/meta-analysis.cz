MAIVE corrects a meta-analysis for publication bias and for the p-hacking that runs through reported standard errors — estimates made to look more precise than their samples can support. It needs one column ordinary meta-analysis does not: the sample size behind each estimate.

What you need

One row per estimate.
effectthe reported estimate
seits standard error
n_obsthe sample size behind it
study_idoptional; add it when a study reports more than one estimate and MAIVE will cluster on it

Ordinary meta-analysis needs the first two. MAIVE needs the third. That is the whole extra ask, and it is why every dataset here ships those column names.

Run it

The web app at easymeta.org takes a spreadsheet and needs no code. To call it directly, POST to the free API — no key, no sign-up:

curl -s https://api.maive.eu/v1/run-model \
  -H 'Content-Type: application/json' -d '{
  "data": [
    {"effect": 0.42, "se": 0.11, "n_obs": 120, "study_id": "Smith2020"},
    {"effect": 0.31, "se": 0.06, "n_obs":  90, "study_id": "Smith2020"},
    {"effect": 0.55, "se": 0.20, "n_obs":  45, "study_id": "Jones2019"}
  ],
  "parameters": {"modelType": "MAIVE", "useLogFirstStage": true,
                 "standardErrorTreatment": "clustered_cr2"}
}'

The parameters must be nested under parameters. Sent at the top level they are silently ignored: you get HTTP 200, default settings, and no warning. Use the synchronous endpoint above — the asynchronous one ignores modelType and runs MAIVE whatever you ask for.

Ask an AI to run it

Give an assistant your data and this, and check what it reports against the three numbers below.

Run MAIVE on my data with the free EasyMeta API and report the result.

POST https://api.maive.eu/v1/run-model  (no API key needed)
  {"data": [{"effect": .., "se": .., "n_obs": .., "study_id": ".."}, ...],
   "parameters": {"modelType": "MAIVE", "useLogFirstStage": true,
                  "standardErrorTreatment": "clustered_cr2"}}

study_id is optional; include it if a study reports several estimates.

Three things that will silently give you the wrong answer:
- Parameters MUST be nested under "parameters". At the top level they are ignored
  and you get defaults, with HTTP 200 and no warning.
- Use this synchronous endpoint. The async one (/v1/runs) ignores modelType.
- Check firstStage.mode is "log" in the response. If it says "levels", the
  parameters did not take effect, so fix the nesting and run again.

Then: if firstStageFStatistic is below 10 the instrument is weak, so do not quote
effectEstimate. Re-run with "computeAndersonRubin": true and report andersonRubinCI,
and also run RTMA at /v1/run-rtma. Otherwise report effectEstimate, standardError,
the first-stage F, and publicationBias.pValue. Do not invent numbers.

A worked example

The excess sensitivity of consumption to anticipated income: 3,127 estimates from 144 studies, the whole dataset, unmodified.

Simple mean of the literature0.373
MAIVE0.195 (0.010)
WAIVE0.081 (0.007)

The hollow points are what the studies reported; the filled points are what MAIVE instruments them to. Publication bias costs roughly half the effect. The paper's own correction, which also removes aggregation bias, lands at 0.11.

Read three numbers before the estimate

firstStage.modelog — if this says levels, your parameters never took effect
firstStageFStatistic346.8 — below 10 the instrument is weak and the point estimate should not be quoted
publicationBias.pValue2e-105 — whether there was bias to correct at all

If the first stage is weak

Restrict the same literature to instrumental-variable estimates on panel data — 294 estimates from 21 studies, one of the dataset's own coding dimensions — and the first stage collapses to F = 0.85.

MAIVE still returns a number, 0.462 (0.453). Do not quote it. Re-run with "computeAndersonRubin": true and report the interval instead: [-0.481, 1.593], which is wide and contains zero. An Anderson–Rubin interval inverts a test rather than being built from the point estimate, so it need not contain that estimate.

Then run RTMA at /v1/run-rtma, which does not depend on the instrument: μ = 0.401, 95% CI [0.306, 0.582]. Check its diagnostics before quoting it — here R-hat is 1.002 with 0 divergent transitions, so the fit is sound.

If you suspect p-hacking

Send "modelType": "WAIVE", which downweights estimates whose precision the sample size does not support: 0.081 (0.007) against MAIVE's 0.195.

Suspect, not demonstrated: this literature shows no significant bunching of t-statistics just above 1.96 (350 against 321, p = 0.28). WAIVE is the estimator to reach for when you have reason to think reported precision is manufactured, not a verdict that it was.

What this does not fix

MAIVE removes bias that runs through the standard error. It does not repair an estimate whose standard error is honest but whose specification was hacked — dropped controls, sample cuts, outcome switching. No method that reads only effect, standard error and sample size can.

It also needs a standard error that is not simply arithmetic in the sample size. For partial correlation coefficients, SE = √((1−r²)/(n−2)) by construction, so regressing log SE on log n returns a slope of −0.5 and an enormous F that is a tautology rather than a strong instrument. If that regression has an R² near 1, MAIVE has nothing to instrument away.

This is newer than the paper

The Nature Communications paper runs the first stage in levels. The app and the API are newer, and we recommend the log first stage used throughout this page — "useLogFirstStage": true. It is not a cosmetic difference: on some literatures the two forms give first-stage F statistics two orders of magnitude apart, and levels can call a strong instrument weak. Where this page and the paper disagree, the page is the more current advice.
